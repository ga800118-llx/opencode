# Skill 冷启动就绪设计

## 目标

修复桌面应用首次启动后打开“设置 > Skill”时，已安装 Skill 短暂或持续显示为 0，刷新页面后才显示真实列表的问题。

完成后，Skill 管理页应在第一次进入时等待 Skill 数据源完成初始化，并直接展示当前已安装的 Skill。真实空列表仍然可以正常显示空状态。

## 已观察到的故障

- 桌面应用冷启动后，Skill 管理接口首次请求可能返回空数组。
- 同一进程中刷新渲染页面后，再次请求可以返回 17 个 Skill。
- 当前前端把任何成功的空数组立即解释为“尚未安装 Skill”。
- 当前后端会在后台启动内部插件；Skill 和 ConfigSkill 也包含在这批异步启动任务中。
- Skill 接口虽然等待对应插件进入 active 状态，但冷启动路径仍未保证首次管理快照一定来自完成初始化的数据源。

## 设计决策

采用两层防护：

1. 后端建立 Skill 专用的初始化就绪屏障，消除首次请求读取未完成状态的根因。
2. 前端对首次成功但为空的结果做短时、有限重试，避免兼容旧后端或极端调度情况下闪现错误空状态。

不把所有内部插件都改为同步启动，以免扩大启动耗时和改动范围。

## 后端就绪屏障

在 `PluginInternal.locationLayer` 中，将以下两个内部插件从后台批次移到同步初始化批次：

- `SkillPlugin.Plugin`
- `ConfigSkillPlugin.Plugin`

Location layer 返回前必须完成这两个插件的注册和加载。其余内部插件继续按现有方式在 scoped fiber 中后台启动。

同步批次保持 Skill 在前、ConfigSkill 在后的现有顺序，并从后续后台批次中删除这两个插件，避免重复注册。

Skill HTTP handler 现有的 `PluginV2.wait("skill")` 和 `PluginV2.wait("config-skill")` 保留，作为请求边界上的第二道后端保护。

## 前端防护

Skill 管理列表第一次加载时：

- 非空结果立即返回并渲染。
- 空数组触发有限重试。
- 最多执行 3 次请求，重试间隔依次为 100ms、200ms。
- 重试期间维持加载状态，不显示“已安装 0 个”或“尚未安装 Skill”。
- 3 次请求均为空时，接受它为真实空列表并显示现有空状态。

该逻辑放在 Skill 管理的数据加载边界中，不改变全局查询重试策略。这样可以只处理“成功但初始化未完成”的领域状态。

HTTP 错误不使用这套空列表重试；错误继续走当前查询失败路径，避免掩盖网络、权限或服务端异常。

## 状态与交互

- 首次加载：显示现有加载状态。
- 首次返回非空：立即显示列表和正确数量。
- 首次返回空、后续返回非空：持续显示加载状态，随后显示列表，不闪现空状态。
- 有限重试后仍为空：显示真实空状态。
- 请求失败：显示现有失败状态，不伪装为空列表。

启用、禁用、删除、来源和简介等既有管理行为不变。

## 测试

后端测试应覆盖：

- Location layer 完成时，Skill 和 ConfigSkill 已经可用。
- 第一次 Skill 管理快照可以读取内置或共享 Skill，不依赖第二次请求。
- 其他内部插件仍可保持后台启动，不要求整个插件系统同步完成。

前端测试应覆盖：

- 第一次返回空数组、第二次返回 Skill 时，最终显示 Skill 且不进入空状态。
- 第一次返回非空时只请求一次。
- 连续 3 次为空时停止重试并显示真实空状态。
- HTTP 错误不会触发空列表重试。

完成自动化测试后，在桌面应用冷启动环境中进行一次真实验证：首次打开 Skill 管理页应直接显示已安装列表，无需刷新。

## 非目标

- 本次不提供新建 Skill 界面。
- 本次不改变 Skill 的扫描目录、来源分类或删除权限规则。
- 本次不把插件、MCP 或浏览器工具统一伪装成 Skill。
- 本次不调整整个桌面应用的启动流程或所有插件的加载策略。
